## What is prepared

- `EMCROWN_DATABASE_SCOPE` accepts only live or staging. Table/enum definitions,
  account functions, rate-limit SQL, diagnostics, runtime checks and cookie names
  follow the selected namespace. Live remains the default without an env change.
- A staging process requires the staging login in its connection URL, review mode
  enabled, a valid test-inbox list and SMS explicitly disabled before application
  connections are created. Metadata readiness also rejects privileged/owner roles,
  role memberships, public-schema CREATE or access to the live schema.
- A fresh staging SQL artifact reuses the existing migrations with fixed namespace
  and runtime-role substitutions. Historical migration files/snapshots are not
  modified. Security-definer function bodies/search paths and grants are scoped
  to staging. The versioned grant recipe is infrastructure/database/runtime-grants.sql.
- A staging-only hash ledger records the canonical SQL versions used. The bootstrap
  refuses to overwrite an existing staging schema or role. It is not an incremental
  stage-upgrade tool; future updates/reset require separate review.
- The script creates a NOLOGIN role. It includes no password, live-data copy, live
  table alterations or changes to live grants. It requires the shared btree_gist
  extension to exist already; it does not install shared extensions.
- Review inbox enforcement covers account reset/invitation mail and all appointment
  recipients. It does not by itself create or select staging data.

## Local proof already run

```sh
npm run staging:prepare
npm run test:staging
npm run test:worker
npm run test:auth-mail-review
```

The PostgreSQL test requires installed PostgreSQL 16 server binaries and opens a
loopback-only temporary server using generated credentials and verified TLS.
It uses fictional data only. It creates both namespaces, applies the real schema
bootstrap, and checks database-enforced cross-schema read/update/function and
SET ROLE denials. Running the staging worker leaves the live test queue untouched;
running the live worker handles only its live fixtures. Each processes an account
email and an appointment email through the actual worker code. SMTP is replaced
in memory, so no external email is sent. The actual Lambda bundle separately
passes read-only readiness in both scopes. The local cluster is stopped afterward;
its private temporary data directory is retained rather than automatically deleted.

These tests do not access the project's Supabase URLs or patient data, and they
do not establish hosted pooler authentication or actual AWS delivery acceptance.

## Rollback and maintenance

Disable the staging worker/schedule and stop the staging app to pause testing.
Do not alter the live site's scope to perform a rollback. Do not automatically
DROP schemas or roles: later deletion/reset requires explicit operator approval.
Staging remains separate data within shared infrastructure; it cannot protect the
live service from every shared-capacity or owner-privilege mistake. Keep production
schema changes separate from this one-time staging bootstrap.
